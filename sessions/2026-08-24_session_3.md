# Session 3 — Secrets

**Date:** 2026-08-24
**Branch:** `feature/session-3-secrets` (worktree `.claude/worktrees/session-3-secrets`)

The adapters named in the CLI's design need API keys, and klin had no secrets
handling of any kind: a repo-wide grep for `secret`, `token`, `credential`,
`keyring`, `getenv` and `dotenv` returned nothing in `klin/`, `tests/` or
`.github/`. This session researched what Windows offers in place of the macOS
Keychain, then built the layer.

## The research

`research/2026-08-24_secrets-on-windows.md` surveys Credential Manager, DPAPI,
Windows Hello, the KeePass family, PowerShell SecretStore, `op`/`bw`/`pass`,
plaintext files and cloud vaults, with what each lacks and what mitigates it.

Two findings decided the design. Windows has no per-application ACL on stored
credentials, so anything running as the user reads anything that user stored
(MITRE ATT&CK T1555.004); that is an operating system property and no library
closes it. And Credential Manager blobs are encrypted with the logon session
key, so they do not survive a profile rebuild or the board replacement Barinn's
backup playbook is written against.

So the answer is two layers rather than one store. A KeePassXC database is the
system of record, because it is a file that survives the machine and it locks
behind a prompt. Windows Credential Manager is a cache seeded from it by hand,
because an audit in CI cannot stop to ask a human anything.

## What shipped

`klin/secrets.py` and a `secret` verb with `set`, `get`, `list`, `rm` and
`doctor`. Lookup order is `KLIN_SECRET_<NAME>`, then whichever conventional
variable the manifest declares, then an external reference, then the store. The
environment comes first so CI never reaches for a vault, and so an SSH session
works, which is precisely where Credential Manager is unreachable.

`manifest.secrets()` validates an optional `secrets:` block of names and
references. `ledger.sanitise()` strips credential-shaped query parameters from
record URLs on `add`, because a fetch adapter following a presigned link would
otherwise commit the token. CI gained a `windows-latest` entry, since the
credential store is the only part of klin whose behaviour differs per platform.

`keyring` is the second runtime dependency and the first with a platform
backend. On Windows it pulls only `pywin32-ctypes`, which is pure-Python
`ctypes`, so the no-compiler install story holds.

## Three things the build turned up

**keyring cannot enumerate a vault.** The backends expose get, set and delete
against a known name and nothing else, so `secret list` had no way to show what
was stored. klin now keeps its own index under a reserved name. Losing it costs
the listing, never a value.

**`keepassxc-cli db-create` produces KDBX 3.1**, not KDBX 4, and only KDBX 4 can
use Argon2. Found by reading the outer header of a database created with the
exact commands the docs then gave. KDBX 3.1 falls back to AES-KDF, which a GPU
parallelises cheaply, and the `-t` flag tunes iterations without making it
memory-hard. For a database whose whole defence is its KDF once a copy is synced
offsite, that is the difference that matters. Three places in the research doc
had asserted Argon2 as a property of the file rather than of the format.

**An empty passphrase is invisible to that check.** `db-create -p` accepts an
empty value if you press enter through the prompt, and the outer header records
the KDF without recording which key components exist, so an unprotected database
reports the same strong Argon2 parameters as a good one. Opening with the
password key deactivated is the check that catches it: it has to fail. Windows
Hello quick unlock also fails in that state, for a reason that looks unrelated,
because it works by encrypting credentials that do not exist.

## Decisions worth recording

**One database per person, not per project.** Splitting per repository
multiplies custody without splitting risk: each would need its own passphrase,
sync, backup and restore drill. klin originates the convention and does not own
the file. Groups inside one database do the separation, so a project-only secret
lives under that project's group and is absent from that project's klin
manifest. The test for the `secrets:` block is narrow: does a klin adapter read
it? The rclone crypt password is a secret and belongs in the database, but
nothing in klin will ever ask for it.

**An agent reads the cache and never the database.** Handing an agent the
passphrase puts the root credential in a command string, a transcript, and
whatever archives that transcript, and that one credential opens every group.
The cache holds read-scoped tokens that are cheap to rotate. A key file looks
like the way around this and is worse: it turns the root credential into a file
readable by anything running as the user, which is the gap the whole
investigation is about.

**A declared `ref` raises rather than falling through to the store.** A
reference the tool cannot follow is a broken promise, and quietly serving a
cached value instead is the silent fallback the research document objects to
everywhere else. So nothing declares a `ref` until a resolver exists.

## Verified by hand, not only by tests

Against real Windows Credential Manager: store, list, read, oversize rejection
and removal, with `cmdkey /list` confirming the local-machine persistence pin
took effect. The full KeePassXC pipeline was dry-run against a throwaway
database, then run for real: `keepassxc-cli show -q -s -a Password` piped into
`klin secret set`, read back through `klin secret get`, with `doctor` reporting
the source. The vault at `C:\Users\pilyu\vault.kdbx` is KDBX 4.0 with Argon2d at
64 MiB and 80 iterations, passphrase-protected, synced to `gdrive:vault/` and
restore-drilled for integrity.
