# Session 10: the empty answer that reads as truth

**Date**: 2026-08-28
**Branch**: `feature/session-10-indexguards` (worktree, `.claude/worktrees/session-10-indexguards`)

## Why now

The consuming project ran an audit round and reproduced every number the index
had ever reported, but only after tripping over the same failure twice in one
sitting: a question asked of the index got an empty answer that looked like a
fact about the corpus and was actually an artifact of how the question was
asked. Both were already half-guarded, which is what made them worth a
session — the guard existed, in the wrong place.

## The two guards

**`index status` prints the cache-drift note the ledger audit prints.** The
index database lives beside the cache, deliberately, so a shell that is
missing `KLIN_CACHE` resolves a different index — usually a fresh, empty one
at the default location. In that state `ledger audit` already warned (session
6 built that note), but `status` reported `0 item(s)` with a straight face.
The audit round hit exactly this: the variable was set at the Windows user
level and the agent shell's process tree predated it, so the environment did
not carry it, and `status` — the very command the consuming project's docs
say to trust over any written-down count — showed an empty index while the
built one sat in `D:\klin-cache`. Same note, second reader, one implementation
(`_report_drift` was already factored out; `cmd_index_status` now calls it).

**`ls --project` names a case miss.** Claims are matched exactly.
`--project barinn` against a claim named `Barinn` returned "nothing in the
index matches", and the auditor read that as the truth about the corpus until
the claim block said otherwise. The hint fires only when the miss is exactly
a case difference against a claim the index actually holds; a genuinely
unknown name still gets the plain empty answer, because guessing would be
worse than silence.

## The third change, found while testing the first

The test suite inherited the developer's real `KLIN_CACHE`. `cache_dir`
resolves the environment before the manifest, so a user-level variable leaks
into every fixture repo, and drift behaviour in tests depended on whose
machine the suite ran on. The full suite happened to pass with the variable
set — verified before touching anything, 372 green — but that is luck, not
design, and the new status tests would have been order-dependent under it.
`conftest.py` now deletes the variable the way it already nulls the real
keyring; a test that wants a cache sets one explicitly.

## Verified

375 tests (372 + 3). Both guards also proven live against the consuming
project's real corpus: `status` in a shell stripped of `KLIN_CACHE` prints
the note under the suspicious path and names the three trees the 17 recorded
files actually live in, and `ls --project barinn` answers "the index has
'Barinn', not 'barinn'".
