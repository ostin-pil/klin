# Session 5 — Reading the licence the vendor actually published

**Date:** 2026-08-24
**Branch:** `feature/session-5-licence` (worktree `.claude/worktrees/session-5-licence`)

Barinn's session 7 ran the screenshot test against the adapters session 4
shipped, and filed two follow-ups against klin. This session takes the first,
and finds the second was not a defect.

## The defect

`klin fetch hf` read the `license:` tag and stopped. For an SPDX identifier that
is correct and complete. For `license: other` it was neither, because `other` is
the Hub saying "not on our list" — a statement about its own vocabulary, not
about the licence — and a card that sets it almost always sets two more fields
beside it:

```
Comfy-Org/flux1-dev      license       other
                         license_name  flux-1-dev-non-commercial-license
                         license_link  .../FLUX.1-dev/blob/main/LICENSE.md
```

So klin reported the two largest models Barinn fetches as unclassifiable while
the vendor's answer sat two fields below in the same API response, with the word
in the name. Session 7 caught it because rule 5 fired three times against the
ledger and was right every time.

Asking for a hand classification in that state is worse than not asking. It
teaches the reader that the question is unanswerable, when it has in fact been
answered and the tool simply stopped reading.

## What changed, and the line that did not move

All three fields are read now, and the terms are fetched from the link rather
than only from the repository being downloaded. That second half matters more
than it looks: `license_link` points at whichever repository owns the terms,
which for both FLUX derivatives is `black-forest-labs/FLUX.1-dev` and not the
repository being fetched. The old fallback looked for a `LICENSE` file in the
wrong repository and mostly found nothing. Flux.1-dev now records 18,491
characters beginning "FLUX.1 [dev] Non-Commercial License v1.1.1", which is
exactly what rule 5 has been asking for.

What did not move is the guess. A licence *named* non-commercial is still not
classified as noncommercial, because deriving a family from a string that
happens to contain a word is the invention this module exists to prevent. The
classification stays `unknown` and a human still decides. What changed is that
the human is shown the name, the link and the terms rather than being asked in
the abstract.

There is a test asserting each half, deliberately adjacent, so that the
distinction survives somebody later deciding a substring is good enough.

## One link is structured data, not a name

The PS1 Style Flux mirror declares `bespoke-lora-trained-license`, and session 7
recorded that as a mirror carrying no evidence. It carries more than it appears
to. Its `license_link` is:

```
https://multimodal.art/civitai-licenses?allowNoCredit=True&allowCommercialUse=Image&allowDerivatives=True&allowDifferentLicense=True
```

That query string is Civitai's permission flags, verbatim and machine-readable.
It is not a name to be pattern-matched, it is the same structured data
`civitai.py` already maps, so it now resolves through that same table and needs
no human at all. One table, two vendors: a second copy of the mapping would be a
second thing to drift, and the tests parameterise both vendors over the same
shapes to keep it that way.

A flag link carrying no flags is treated as malformed rather than as a grant of
nothing. Reading an empty query as "no permissions, therefore noncommercial"
would be a guess dressed as a derivation, and a confident one. It falls through
to `unknown` and a person.

This also puts a hazard on the record. `ledger.sanitise` strips
credential-shaped query parameters from committed URLs, and here the query
parameters *are* the licence. None of these names match the credential pattern
today; there is now a regression test that fails if that pattern is ever
widened, because the failure would otherwise be silent and would destroy
evidence rather than protect it.

## The second follow-up was not a defect

Session 7 filed the prose gate's asymmetry as a klin follow-up: repo docs
disable `hard-wrap` while PR bodies are scanned with it enabled, so a body
wrapped like the docs fails a gate the docs pass. That is accurate, and it cost
session 4 a red build.

It is also deliberate, and `.github/workflows/prose.yml` already says why:
GitHub renders a single newline as a line break, so 80-column wrapping that
reads well in a file renders ragged in a PR body. Both halves were documented in
their own files. Neither is the file anybody opens when the gate goes red, so
the note now also sits in `.prose-mint.toml`, and the answer is to write PR
bodies unwrapped rather than to change either config.

Recorded rather than fixed, because the fix would have been wrong.

## Verified against the live API

  through the API.
