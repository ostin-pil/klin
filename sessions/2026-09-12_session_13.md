# Session 13: one generator that never ran, and a second that pins its supply

**Date**: 2026-09-12
**Branch**: `feature/session-13-genadapters` (branch, primary checkout)

## Why now

The consuming project's session 36 built and proved a Hi3DGen environment,
ran the first generation experiment through it, and found on the way that
`klin gen trellis` has never produced a mesh. Both facts point here: one verb
is broken and the other does not exist, while the scripts that actually did
the work live in the consuming project's `scripts/bench/`. A bench script asks
nobody about licences, which is the whole reason these are verbs.

## `gen trellis` had never once produced a mesh

Its in-venv half imported `o_voxel.pipelines.OVoxelImageTo3DPipeline`, a module
that exists in no version of the install. The file had one commit, made the day
the tooling moved into klin, so the verb has failed on its first import for its
entire life. Everything anyone has ever attributed to it — rounds 14 and 16 of
the consuming project's generation benchmark, and session 36's TRELLIS.2 plates
— came from that project's own scripts.

Reproduced before changing anything: `ModuleNotFoundError: No module named
'o_voxel.pipelines'`, in about a second, before any weight loads.

Ported from the script that made those rounds, with the install's own
`run_batch.py` as the second witness for every call:

- the pipeline is `trellis2.pipelines.Trellis2ImageTo3DPipeline`, and the
  exporter is `o_voxel.postprocess.to_glb` called with the mesh's volume,
  coords, layout and voxel size — not a `to_glb` method, which the mesh does
  not have;
- `pipeline.run` returns a list of meshes, not a dict;
- the tier is `pipeline_type` on `run`. It is not a checkpoint, and treating
  it as one meant the licence pre-flight asked the ledger about
  `trellis2-1024_cascade`, a name nothing has ever been recorded under. So the
  verb reported an untraceable model for no reason but its own naming;
- the flex_gemm triton shim, absent from the adapter and present in every
  script that worked, without which this machine's build fails;
- `PYTORCH_CUDA_ALLOC_CONF` at module scope, ahead of any torch import.

**Verified against round 16 on the same input, seed and tier**: 191,502 faces
in 48.2 s at 3.36 GB peak, against round 16's 192,327 in 47.8 s at 3.4 GB.

## `gen hi3dgen`, and what a pins file is worth

The second generator, from the consuming project's `hi3dgen_run.py`. Hi3DGen is
TRELLIS-derived with kaolin, nvdiffrast and flexicubes removed upstream, so
unlike TRELLIS there is nothing to patch and no texture bake to avoid. Both
adapters still carry the same evidence — the NVIDIA modules refused at the
import system, and a mesh out the other side — because a licence file is not
proof of what a transitive import does. This one refuses kaolin and flexicubes
as well, which are precisely what upstream says it dropped.

Two upstream paths are stepped around rather than copied, both of which cost
session 36 a day:

- the demo's local StableNormal load passes `pretrained=True`, which
  `StableNormal_turbo` rejects, and a bare `except` then falls through to
  downloading GitHub's main branch — so upstream never runs its own local copy;
- when background removal finds no object, StableNormal masks the image with a
  BiRefNet it fetches by hub id. It is handed the pipeline's pinned one
  instead. `foreground_found` reports which path a run took, because the frame
  that takes the second one comes back as a slab of the whole image.

**What this adapter adds over the TRELLIS one is the pins.** Hi3DGen pins
nothing it downloads; `from_pretrained`, `torch.hub.load` and that masking step
each take whatever is behind a name today. Session 36 found two of the five had
moved far enough to break the pipeline, and it surfaced as a code bug rather
than as a supply change. So `pins.json` is read as a licence surface — six
sources with revisions and licences, which is the first time a klin generator
can name its whole stack rather than one checkpoint — and its 33 paths are
checked for presence and size before anything starts. A run refuses when one is
not as pinned, because an offline run against unrecorded files proves nothing
about what ran.

Sizes, not hashes. Hashing 7 GB before every run buys what the fetch step
already gives; what this catches is the failure that actually happens, which is
a file gone or replaced.

**Verified**: 415,366 faces, watertight, 12.8 s sampling, 0.4 s exporting,
11.38 GB peak. Session 36's own run gave 415,386 faces and 10.6 GiB, which is
the same 11.38 GB.

## Both are offline now

Hi3DGen already was. TRELLIS was not, and the reason is worth stating because
it is not obvious: `from_pretrained` resolves the pipeline config and every
model through `hf_hub_download`, so a run with a fully warm cache still sends
HEAD requests to huggingface.co and takes whatever answers them. A warm cache
is not the same as no network. Both adapters now set `HF_HUB_OFFLINE` and
`TRANSFORMERS_OFFLINE` on the subprocess, Hi3DGen additionally replaces
`torch.hub`'s downloader with one that raises, and `--online` is how a first
fetch is asked for out loud. The run line says which way it went, since that is
now a property of the run rather than of the machine.

## Two things the runs settled in passing

- **The seed does not fully determine a TRELLIS.2 mesh.** Two runs at one
  input, seed and tier gave 191,502 and 191,438 faces. So the 0.4% gap against
  round 16 is the tool's own run-to-run spread and not the ported path
  differing, and every triangle count in that record should be read as ±0.5%.
- **The first draft of the Hi3DGen peak was mislabelled.** It read
  `max_memory_allocated()` twice after the same reset and called one of them
  the whole process, which would have understated what the run needs on the
  card. The loading peak is now read before the reset and the process figure is
  the larger of the two.

## The three remaining conform follow-ups

All three had been on the consuming project's list since session 12, and none
had a test — which is why the suite stayed green through every one of them.

- **The staged filename followed the source basename, not `--id`.** A pack
  shipping one `bar.obj` with a counter and a stool in it is the ordinary case;
  conforming it twice staged the second file over the first silently, leaving
  two records, one file, and the first record pointing at the second's
  geometry.
- **`--out` could not name a directory that did not exist yet.**
  `os.path.isdir` is false for a path nobody has created, so `--out
  D:/bench/round18` was read as a file called `round18` in `D:/bench`, and the
  export then failed inside Blender with an error naming the temporary working
  path rather than the `--out` given. The extension discriminates now, since
  the only file this verb writes is a `.glb`.
- **A `prefer` rule nagged the project's own work.** Barinn's rule 1 prefers
  CC0 over CC-BY, and it was warning that the project's own lathe props are
  "not public-domain" — asking it to find a more permissively licensed version
  of a thing it wrote itself. A prefer rule is a choice between things one
  could have acquired instead, and own work had no alternative. Only prefer
  skips; a deny is a safety rule and still runs over everything.

Seven tests, four of which fail on the code before the fix. The other three are
guards that each fix stops where it should: a `.glb` `--out` is still a file, a
share-alike record is still denied even when authored here, and an acquired
record is still nagged. Verified against Barinn's real ledger — the
`barinn-authored-props` warning is gone and the remaining 6 failures and 17
warnings are the model records, untouched.

## What this leaves

- **The follow-up list is empty.** All three are fixed above; nothing from
  session 12's list is outstanding.
- **The environment half is still the consuming project's.**
  `hi3dgen_env_check.py` and `hi3dgen_fetch.py` build and pin the venv, and
  klin only consumes what they leave. Whether klin should build environments is
  a real question and was not answered here.
- **`--pins check` verifies presence and size only.** The hash pass stays in
  `hi3dgen_fetch.py --check`.
- **Nothing in either adapter is in the ledger**, so every pre-flight reports
  "(no record)" and `--check` refuses. That is correct — no generated mesh has
  shipped — but it means the pre-flight has not yet been seen passing.
