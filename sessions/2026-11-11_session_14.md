# Session 14: the clean geometry path ran a non-commercial model over every opaque image

**Date**: 2026-11-11
**Branch**: `feature/session-14-rembg` (worktree, stacked on session 13's open PR #12)

## Why now

A research follow-up on agent-driven asset pipelines (11 Nov 2026) confirmed
Pixal3D's code and weights as MIT and then named what its default pipeline pulls
in anyway: RMBG-2.0 under CC BY-NC and nvdiffrast under NVIDIA's non-commercial
licence. A survey of the consuming projects against that note found the same
remover sitting in TRELLIS.2: Barinn's first TRELLIS.2 probe used RMBG-2.0 for
background removal, Puri's STATE already says not to run `trellis2-spz` as
installed because it loads RMBG-2.0, and `klin gen trellis` blocked three NVIDIA
modules and mentioned no remover at all.

## What was actually there

Read in the install, not inferred:

- `pipeline.json` for `microsoft/TRELLIS.2-4B` (snapshot `af44b45`) builds
  `rembg_model` as `BiRefNet(model_name="briaai/RMBG-2.0")`.
- `preprocess_image` runs that remover over any input whose alpha is absent or
  all 255. A generated concept image is almost always opaque.
- The stableprojectorz wrapper, `trellis2/pipelines/rembg/BiRefNet.py`, loads
  `MODELS/RMBG-2.0` relative to the working directory or the script whenever a
  `config.json` is there, and **ignores `model_name`**. The install's
  `code/models` is a link to `D:/trellis2-spz/models`, which holds RMBG-2.0, and
  Windows resolves `MODELS` case-insensitively. So renaming the model in the
  config would have changed nothing.

The import blocker could not have caught this. Nothing restricted is imported:
the restricted part is weights, loaded by the same `transformers` call as any
other model. Session 8's claim, "no restricted module could be imported", was
true and was not the whole claim.

## The fix

`_inside_trellis.py` replaces `trellis2.pipelines.rembg.BiRefNet` before
`from_pretrained` looks it up by name, so the install's wrapper is never
constructed. The replacement builds klin's `Remover`:

- With a directory (`--rembg`, `TRELLIS_REMBG`, or `trellis_rembg` in the
  manifest) it loads that BiRefNet and masks the way the wrapper did.
- Without one it loads nothing, and refuses by name when called. A masked image
  never calls it, so masked input runs exactly as before.
- After the pipeline is built, `confirm_remover` refuses a pipeline whose
  remover klin did not build, which covers a config naming some other class.

The run reports `remover: {configured, loaded, called}`. The outer half prints
which remover masked the image or that none was needed, fails a run that loaded
a remover other than the one it was given, and fails a run that reports no
remover at all.

### Loading the MIT BiRefNet took a second attempt

The directory Hi3DGen already pins, `ZhengPeng7/BiRefNet` at `6a62b7d` (MIT),
does not load through `AutoModelForImageSegmentation.from_pretrained` under the
TRELLIS venv's transformers 4.57: weight tying calls
`config.get_text_config()`, and BiRefNet's own `Config` has no
`is_encoder_decoder`. The install's RMBG-2.0 copy of `birefnet.py` carries a fix
for exactly that, but it is briaai's file, so borrowing it would bring back the
licence this replaces.

`load_birefnet` builds the class from the directory's own code with
`get_class_from_dynamic_module`, puts the safetensors in by name, and refuses on
any missing or unexpected key, because a partial load masks images with a
partly random network and the masks still look plausible. Measured outside the
pipeline first: 0 missing, 0 unexpected, and the mask agrees with the input
image's original alpha on 99.93% of pixels.

Against `C:/Users/pilyu/trellis2-spz/code`, patch state `patched`, from a
throwaway project with a minimal manifest. The input is Overdude's B32 CRT,
`D:/b32/raw/hi3dgen_a42.input.png`, saved once as opaque RGB and once as its
original RGBA:

| Run | Remover | Result |
|---|---|---|

All three had nothing restricted loaded.

## A trap found on the way: `uv run --with .` serves a stale klin

The second real run failed with the error the fix had already removed. `uv run
--with . klin` installs klin from a cached wheel built the first time it ran
and does not rebuild when the source changes, and neither does
`--reinstall-package klin`. `python -I -c "import klin; ..."` showed the
installed `_inside_trellis.py` predating the edit, while a plain `python -c`
showed the checkout, because `-c` puts the working directory on the path.

The gate itself is unaffected: `python -m pytest` also puts the working
directory first, so the suite imports the checkout. A real run through the CLI
needs `uv run --with-editable . klin ...`. The manifest's gate comment, "`--with
.` installs the package from the checkout, so the gate always tests
working-tree code", is right about the result and wrong about the reason.
